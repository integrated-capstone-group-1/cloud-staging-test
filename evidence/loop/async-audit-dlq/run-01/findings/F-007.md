# F-007 Cross-customer IDOR vulnerability on GET /api/v1/ledger/audit/{id} exposing financial ledger audit records
Status: VERIFIED

## Breaker section
Severity:         S1
Oracle:           F7
Domain / journey: async-audit-dlq, E2E-10
Attack area:      Area 3 (Authorization & IDOR)
Reproducibility:  3 of 3 attempts (100%)
Reproduction:
```bash
# 1. Authenticate as Customer A (Juan) and obtain a transaction ID
curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"juan.delacruz@example.com","password":"password123"}'

# 2. Authenticate as Customer B (Maria)
curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"maria.santos@example.com","password":"password123"}'
# Extract Maria's Bearer token <maria_jwt>

# 3. Query Customer A's ledger audit trail using Customer B's token
curl -s -X GET http://localhost:8080/api/v1/ledger/audit/<juan_txn_id> \
  -H "Authorization: Bearer <maria_jwt>"
```
Expected:         docs/CONTRACTS.md line 14 & Section 2.6: Access to transaction details and audit records must be authorized against the authenticated customer's identity. Cross-customer access must be rejected with HTTP 403 Forbidden (ACCESS_DENIED). Per Security Override P-01 & Oracle F7, cross-customer data exposure returning 2xx is an S1 violation.
Actual:           HTTP 200 OK returned to Customer B, leaking Customer A's complete double-entry mutation audit records (internal account IDs, mutation UUIDs, leg numbers, debit/credit directions, amounts, currency, and audit timestamps):
```json
{
  "success": true,
  "message": "OK",
  "data": [
    {
      "mutationUuid": "ea542fdc-5c8d-46d8-9419-fc953e62b205",
      "txnId": "f20f9b72-3ae5-47c3-bccf-5fe690e4a1af",
      "accountId": "3722f77f-3d1b-4d55-8f83-b71bac91d095",
      "legNo": 1,
      "mutationAmount": 10.0000,
      "currencyCode": "PHP",
      "mutationType": "DEBIT",
      "txnType": "TRANSFER"
    }
  ]
}
```
Invariant output: Global invariant check passed (exit 0); read-only authorization leak.
Observed scope:   Affects `GET /api/v1/ledger/audit/{id}` for any valid transaction ID.

## Fixer section (fixer only)

### Step E Proposal
- **Classification:** CODE_BUG
- **Owner:** Rohan (`transaction-service`)
- **Root Cause:**
  1. `TransactionService.findAuditByTxnId` validated authorization using `ownsLeg = audits.stream().anyMatch(...)`. In a double-entry ledger transfer (e.g. Juan transferring to Maria), Maria owns the recipient credit leg, which erroneously passed the check and allowed Maria to retrieve the full audit record including Juan's private debit account ID, mutation UUIDs, and business dates.
  2. Per `docs/CONTRACTS.md` line 14 & Section 2.6, transaction ownership belongs to the initiating customer (`master.getCustomerId()`).
  3. `TransactionService.findAuditByAccountId` caught `Exception` generically without propagating `AccessDeniedException`.
- **Files Affected:**
  - `transaction-service/src/main/java/com/capstone/transaction/service/TransactionService.java`
- **Diff Summary:**
  - Updated `findAuditByTxnId` to check `master.getCustomerId()` via `SecurityUtils.checkCustomerAccess(master.getCustomerId(), "view audit for transaction " + txnId)`.
  - Added fallback to check initiating (DEBIT) leg ownership when master record is absent.
  - Updated `findAuditByAccountId` to explicitly rethrow `AccessDeniedException`.
