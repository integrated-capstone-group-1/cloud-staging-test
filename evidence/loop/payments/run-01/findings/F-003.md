# F-003 Monetary amount with scale exceeding 4 and scientific notation accepted on payment endpoint
Status: VERIFIED

## Breaker section
Severity:         S1
Oracle:           F3, F8
Domain / journey: payments, E2E-02
Attack area:      Area 1 (Input)
Reproducibility:  3 of 3 attempts (100%)
Reproduction:
```bash
# 1. Authenticate as customer
curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"juan.delacruz@example.com","password":"password123"}'
# Extract Bearer token <jwt>

# 2. Submit payment with scale > 4 decimals (e.g. 6 decimals: 10.123456)
curl -s -X POST http://localhost:8080/api/v1/payments \
  -H "Authorization: Bearer <jwt>" \
  -H "X-Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "recipient_account_id": "f95e7e52-3259-4b4d-ac66-b186a893cf66",
    "amount": "10.123456",
    "currency": "PHP"
  }'

# 3. Submit payment with scientific notation ("1e3")
curl -s -X POST http://localhost:8080/api/v1/payments \
  -H "Authorization: Bearer <jwt>" \
  -H "X-Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "recipient_account_id": "f95e7e52-3259-4b4d-ac66-b186a893cf66",
    "amount": "1e3",
    "currency": "PHP"
  }'
```
Expected:         docs/CONTRACTS.md line 11 & line 163: "amount: decimal string, scale at most 4, strictly greater than 0. Non-numeric, over-scaled, zero or negative: 400 VALIDATION_FAILED." Fixed-point decimals with scale at most 4 (NUMBER(18,4) in DB) to eliminate float precision loss. Oracle F8 forbids accepting amounts with scale > 4.
Actual:           Server accepts the payments with HTTP 202 Accepted (or 200 OK), assigning a transaction_id rather than rejecting with HTTP 400 Bad Request (VALIDATION_FAILED).
Invariant output: Global invariant check passed (exit 0) on pre-settlement status; downstream ledger posting with truncated scale risks truncation or rounding drift.
Observed scope:   Affects `POST /api/v1/payments` for any over-scaled decimal string (`10.123456`, `10.12345678`) and scientific notation string (`1e3`).

## Fixer section (fixer only)

### Step E Proposal
- **Classification:** CODE_BUG
- **Owner:** Rohan (`orchestrator-service`), Transaction (`transaction-service`), Common (`common`)
- **Root Cause:**
  1. `PaymentRequest.java` in both `orchestrator-service` and `transaction-service` lacks scale and format constraints on `BigDecimal amount`. It only declares `@DecimalMin(value = "0.0001")`, without validating that fraction digits cannot exceed 4 or rejecting scientific notation.
  2. Jackson deserializes scientific notation (`"1e3"`) and arbitrary decimal scale (`10.123456`) into `BigDecimal` by default.
  3. `GlobalExceptionHandler.java` does not attach `error_code: "VALIDATION_FAILED"` in `handleMethodArgumentNotValid` and does not override `handleHttpMessageNotReadable` to produce contract-compliant RFC 7807 responses.
- **Files Affected:**
  - `common/src/main/java/com/capstone/common/util/MonetaryAmountDeserializer.java` (new Jackson deserializer enforcing `^[0-9]+(\\.[0-9]{1,4})?$`)
  - `orchestrator-service/src/main/java/com/capstone/orchestrator/dto/PaymentRequest.java`
  - `transaction-service/src/main/java/com/capstone/transaction/dto/PaymentRequest.java`
  - `common/src/main/java/com/capstone/common/exception/GlobalExceptionHandler.java`
- **Diff Summary (Proposed, not applied):**
  - Create `MonetaryAmountDeserializer` checking strict fixed-point regex (`^[0-9]+(\\.[0-9]{1,4})?$`), rejecting scientific notation and scale $> 4$.
  - Annotate `amount` in `PaymentRequest` (both `orchestrator-service` and `transaction-service`) with `@JsonDeserialize(using = MonetaryAmountDeserializer.class)` and `@Digits(integer = 14, fraction = 4, message = "amount scale cannot exceed 4 decimal places")`.
  - In `GlobalExceptionHandler.java`:
    - Add `pd.setProperty("error_code", "VALIDATION_FAILED")` in `handleMethodArgumentNotValid`.
    - Override `handleHttpMessageNotReadable` to return `400 Bad Request` with `error_code: "VALIDATION_FAILED"`.
- **Contract Line / Invariant Enforced:**
  - `docs/CONTRACTS.md` line 11: `Monetary Representation: Strings formatted as fixed-point decimals ("50.0000") with scale 4 (NUMBER(18,4) in DB) to eliminate float precision loss.`
  - `docs/CONTRACTS.md` line 163: `amount: decimal string, scale at most 4, strictly greater than 0. Non-numeric, over-scaled, zero or negative: 400 VALIDATION_FAILED.`
- **Contradiction Check:**
  - Standard payments with scale 1 to 4 (`50`, `50.0`, `50.00`, `50.0000`) continue to pass.
  - Non-numeric strings, negative amounts, over-scaled decimals, and scientific notation strings are rejected with `400 Bad Request` and `VALIDATION_FAILED`.
- **Schema / Migration Impact:** None.
- **Regression Test:**
  - JUnit tests in `PaymentForwardingControllerTest.java` and `PaymentOrchestratorTest.java` verifying rejection of `10.123456`, `1e3`, `abc`, `-10.00`.
  - Integration test asserting HTTP 400 `VALIDATION_FAILED`.
  - Blackbox curl replay of F-003 reproduction requests.
- **Commands to run:**
  - `mvn test -pl common`
  - `mvn test -pl orchestrator-service`
  - `mvn test -pl transaction-service`
  - `python tests/invariants/check_invariants.py --scope global --wait-drain 30`
- **Regression Risk:** Low. Additive input validation enforcing existing documented API contracts.
