# F-004 Concurrent payment requests with identical idempotency key leak raw SQL and database schema on ORA-00001 constraint violation
Status: VERIFIED

## Breaker section
Severity:         S1
Oracle:           F2, F4, F5
Domain / journey: payments, E2E-02
Attack area:      Area 2 (Idempotency) & Area 7 (Concurrency)
Reproducibility:  5 of 5 attempts (100% on concurrent requests)
Reproduction:
```bash
# 1. Authenticate as customer
curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"juan.delacruz@example.com","password":"password123"}'
# Extract Bearer token <jwt>

# 2. Fire concurrent identical requests sharing the same X-Idempotency-Key
KEY=$(uuidgen)
for i in {1..5}; do
  curl -s -X POST http://localhost:8080/api/v1/payments \
    -H "Authorization: Bearer <jwt>" \
    -H "X-Idempotency-Key: $KEY" \
    -H "Content-Type: application/json" \
    -d '{
      "recipient_account_id": "f95e7e52-3259-4b4d-ac66-b186a893cf66",
      "amount": "20.0000",
      "currency": "PHP"
    }' &
done
wait
```
Expected:         docs/CONTRACTS.md line 28 & line 160: Concurrent identical requests with the same X-Idempotency-Key while the first request is processing must return HTTP 409 Conflict with error code REQUEST_IN_PROGRESS (via Redis SETNX lock). Responses must never leak SQL, schema, or database errors (Oracle F2).
Actual:           Concurrent requests bypass edge fast-locking and hit the database concurrently. Oracle XE raises an unhandled constraint violation, and the server leaks raw SQL statements and table/constraint metadata in the HTTP 400 response body:
```text
Transaction service error [500]: {"type":"https://capstone.bank/errors/internal","title":"Internal Server Error","status":500,"detail":"An unexpected error occurred: could not execute statement [ORA-00001: unique constraint (LEDGER_APP.UQ_TXN_CUST_IDEMPOTENCY) violated\n] [insert into transaction_master (business_date,cancel_reason,completed_at,core_reference_id,created_at,created_by,credit_account_id,currency_code,customer_id,debit_account_id,dest_amount,dest_currency_code,failure_code,fx_rate,hold_id,idempotency_key,initiated_at,is_cross_currency,mutation_amount,original_txn_id,reversal_of_txn_id,reversal_txn_id,reversed,reversed_by_txn_id,risk_decision,risk_rules,risk_score,stage,txn_status,txn_type,updated_at,updated_by,txn_id) values (?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?)]; constraint [LEDGER_APP.UQ_TXN_CUST_IDEMPOTENCY]"
```
Invariant output: Global invariant check passed (exit 0); database rejected duplicate insert at constraint level.
Observed scope:   Observed on `POST /api/v1/payments` whenever identical idempotency keys are submitted in parallel before the initial transaction commits and writes to cache.

## Fixer section (fixer only)

### Step E Proposal
- **Classification:** CODE_BUG
- **Owner:** Transaction (`transaction-service`), Common (`common`), Rohan (`orchestrator-service`)
- **Root Cause:**
  1. `PaymentOrchestrator.java` does not acquire an in-flight distributed lock (`IdempotencyService.tryLock(idempotencyKey)`) prior to persisting the initial transaction, relying solely on non-locking database reads (`txnMasterRepository.findByCustomerIdAndIdempotencyKey`).
  2. Under concurrent requests with the same key, multiple threads simultaneously execute `createInitiatedTransaction`, triggering the Oracle unique constraint `UQ_TXN_CUST_IDEMPOTENCY` (ORA-00001).
  3. `DataIntegrityViolationException` is not caught or mapped to `IdempotencyConflictException`, causing Spring Boot to bubble a 500 error containing the raw SQL query, database parameters, and constraint name.
  4. In `orchestrator-service`, `TransactionClient.java` maps non-409/422 downstream errors to `IllegalStateException`, wrapping the raw SQL into an HTTP 400 `Invalid State` problem detail.
- **Files Affected:**
  - `transaction-service/src/main/java/com/capstone/transaction/service/PaymentOrchestrator.java`
  - `common/src/main/java/com/capstone/common/exception/GlobalExceptionHandler.java`
  - `orchestrator-service/src/main/java/com/capstone/orchestrator/client/TransactionClient.java`
- **Diff Summary (Proposed, not applied):**
  - `PaymentOrchestrator.java`:
    - Inject `IdempotencyService`.
    - If `idempotencyKey != null`: call `idempotencyService.tryLock(idempotencyKey)` before creating the transaction. If lock fails or indicates in progress, throw `IdempotencyConflictException("REQUEST_IN_PROGRESS: Request with idempotency key '" + idempotencyKey + "' is already being processed")`.
    - Wrap `lifecycleService.createInitiatedTransaction(txn)` in a try/catch: if `DataIntegrityViolationException` occurs on `UQ_TXN_CUST_IDEMPOTENCY`, rethrow as `IdempotencyConflictException("REQUEST_IN_PROGRESS: ...")`.
    - In error handling paths, release the in-flight lock via `idempotencyService.release(idempotencyKey)`.
  - `GlobalExceptionHandler.java`:
    - Add explicit `error_code` property to `handleIdempotencyConflict`: `"REQUEST_IN_PROGRESS"` if message contains `REQUEST_IN_PROGRESS`, else `"PAYLOAD_MISMATCH"`.
    - Catch `DataIntegrityViolationException`: sanitize detail message to `"Database constraint violation"` without exposing raw SQL or schema metadata.
  - `TransactionClient.java`:
    - Ensure 409 responses from `transaction-service` preserve and rethrow `IdempotencyConflictException` with the downstream RFC 7807 error code.
- **Contract Line / Invariant Enforced:**
  - `docs/CONTRACTS.md` line 28: `409 Conflict | REQUEST_IN_PROGRESS | Duplicate X-Idempotency-Key currently processing (SETNX returned 0).`
  - `docs/CONTRACTS.md` line 160: `Same key while the first request is still running: 409 REQUEST_IN_PROGRESS.`
  - Oracle F2: Zero raw SQL or database schema leakage.
- **Contradiction Check:**
  - Sequential requests with the same key and payload continue to replay cached responses.
  - Sibling check: checked other endpoints with idempotency (`/api/v1/cards/virtual`, `/api/v1/transfers`); verified proper locking.
- **Schema / Migration Impact:** None.
- **Regression Test:**
  - Unit test in `transaction-service` simulating concurrent requests with the same idempotency key, asserting exactly one succeeds and concurrent duplicates receive `409 Conflict` (`REQUEST_IN_PROGRESS`).
  - Blackbox curl concurrency script (5 parallel workers sharing key).
- **Commands to run:**
  - `mvn test -pl common`
  - `mvn test -pl transaction-service`
  - `mvn test -pl orchestrator-service`
  - `python tests/invariants/check_invariants.py --scope global --wait-drain 30`
- **Regression Risk:** Low. Enforces distributed lock contract and prevents unhandled DB exceptions from leaking SQL.
