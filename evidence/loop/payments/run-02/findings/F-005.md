# F-005 Cross-customer IDOR vulnerability on GET /api/v1/payments/{id}
Status: VERIFIED

## Breaker section
Severity:         S1
Oracle:           F7
Domain / journey: payments, E2E-02
Attack area:      Area 3 (Authorization)
Reproducibility:  3 of 3 attempts (100%)
Reproduction:
```bash
# 1. Authenticate as Customer A (Juan) and create a payment
curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"juan.delacruz@example.com","password":"password123"}'
# Extract Juan's Bearer token and record generated <txn_id> from POST /api/v1/payments

# 2. Authenticate as Customer B (Maria)
curl -s -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"maria.santos@example.com","password":"password123"}'
# Extract Maria's Bearer token <maria_jwt>

# 3. Query Customer A's transaction using Customer B's token
curl -s -X GET http://localhost:8080/api/v1/payments/<juan_txn_id> \
  -H "Authorization: Bearer <maria_jwt>"
```
Expected:         docs/CONTRACTS.md line 14 & line 176: Caller identity comes only from verified JWT. Accessing another customer's resource must be rejected with HTTP 403 Forbidden (or 404 Not Found per [VERIFY H-05]). Per Security Override P-01 & Oracle F7, cross-customer data access returning 2xx is strictly forbidden and constitutes an S1 violation. Note: Sister endpoint `GET /api/v1/transactions/{id}` correctly enforces this with `403 ACCESS_DENIED`.
Actual:           HTTP 200 OK returned to Customer B, leaking Customer A's transaction details:
```json
{
  "transaction_id": "18a020d1-908c-4a95-8f9a-659357a02313",
  "core_reference_id": "8acf1906-31d2-4146-b46e-bf2780f9dfc1",
  "status": "POSTED",
  "stage": "COMPLETED",
  "paid_amount": 10,
  "paid_currency": "PHP",
  "created_at": "2026-10-10T02:55:55.626593"
}
```
Invariant output: Invariant check passed (exit 0); read-only authorization leak does not mutate balances.
Observed scope:   Affects `GET /api/v1/payments/{id}`. Contrast with `GET /api/v1/transactions/{id}` which properly checks ownership and returns `403 ACCESS_DENIED`.

## Fixer section (fixer only)

### Step E Proposal
- **Classification:** CODE_BUG
- **Owner:** Rohan (`orchestrator-service` and `transaction-service`)
- **Root Cause:**
  1. `PaymentController.getPaymentStatus` in `transaction-service` retrieves `TransactionMaster` by ID (`txnMasterRepository.findById(id)`) and maps it directly into `PaymentResponse` without calling `SecurityUtils.checkCustomerAccess(txn.getCustomerId(), "view payment status")`.
  2. `PaymentController.cancelPayment` in `transaction-service` similarly executes cancellation without calling `SecurityUtils.checkCustomerAccess(txn.getCustomerId(), "cancel payment")`.
  3. In `orchestrator-service`, `TransactionClient.java` lacks an explicit handler for downstream HTTP 403 status from `transaction-service`, causing non-409/422 errors to fall through into generic `IllegalStateException`.
- **Files Affected:**
  - `transaction-service/src/main/java/com/capstone/transaction/controller/PaymentController.java`
  - `orchestrator-service/src/main/java/com/capstone/orchestrator/client/TransactionClient.java`
- **Diff Summary (Proposed, not applied):**
  - `PaymentController.java`:
    - In `getPaymentStatus(@PathVariable("id") String id)`: after fetching `TransactionMaster txn`, if `txn.getCustomerId() != null`, call `SecurityUtils.checkCustomerAccess(txn.getCustomerId(), "view payment status")`.
    - In `cancelPayment(@PathVariable("id") String id, ...)`: fetch `txn` (or verify ownership) before invoking `lifecycleService.cancelPayment(id, reason)`, and call `SecurityUtils.checkCustomerAccess(txn.getCustomerId(), "cancel payment")`.
  - `TransactionClient.java`:
    - Add status 403 handler in `defaultStatusHandler`:
      ```java
      else if (status == 403) {
          throw new org.springframework.security.access.AccessDeniedException(body.isBlank() ? "Access Denied" : body);
      }
      ```
- **Contract Line / Invariant Enforced:**
  - `docs/CONTRACTS.md` line 14: `Caller identity comes ONLY from the verified JWT sub claim... The service MUST verify ownership before reading or mutating the account.`
  - `docs/CONTRACTS.md` line 176: `403 ACCESS_DENIED | Transaction belongs to another customer.`
  - Security Override P-01 & Oracle F7: Cross-customer data access returning 2xx is strictly forbidden and constitutes an S1 violation.
- **Contradiction Check:**
  - Authenticated transaction owner continues to receive HTTP 200 OK.
  - Privileged callers (`ROLE_ADMIN`, `ROLE_INTERNAL`) continue to access any transaction via `SecurityUtils.isPrivileged()`.
  - Sibling check: `TransactionHistoryService.java` (`GET /api/v1/transactions/{id}`) uses this exact pattern and successfully rejects cross-customer queries.
- **Schema / Migration Impact:** None.
- **Regression Test:**
  - WebMvc test / controller security test in `transaction-service` and `orchestrator-service` verifying cross-customer query returns HTTP 403 Forbidden (`ACCESS_DENIED`).
  - Blackbox reproduction curl script asserting Customer B querying Customer A's transaction receives HTTP 403 with `error_code: ACCESS_DENIED`.
- **Commands to run:**
  - `mvn test -pl transaction-service`
  - `mvn test -pl orchestrator-service`
  - `python tests/invariants/check_invariants.py --scope global --wait-drain 30`
- **Regression Risk:** Very low. Directly enforces customer tenancy boundaries per CONTRACTS.md line 176 and Oracle F7.
