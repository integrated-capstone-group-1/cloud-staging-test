## 3. In-Scope Contract Slice
* Implement internal endpoints from [`docs/CONTRACTS.md`](file:///c:/Users/RBS83790/OneDrive%20-%20EastWest%20Banking%20Corporation/Documents/training/integrated-capstone/capstone-banking-system/docs/CONTRACTS.md#L132-L195):
  * `POST /internal/core/settlement`
  * `GET /internal/core/settlement/{posting_reference_id}`
  * `POST /internal/accounts/{id}/holds`
  * `DELETE /internal/accounts/{id}/holds/{holdId}`
* Multi-Row Pessimistic Locking:
  * Sort all involved `account_id` values in ascending alphanumeric order.
  * Execute: `SELECT balance_amount, held_amount FROM account_master WHERE account_id IN (...) ORDER BY account_id FOR UPDATE;`
* Available Balance Calculation:
  $$\text{Available Balance} = \text{balance\_amount} - \text{held\_amount}$$
  Reject debits where `debit_amount > available_balance` with `422 INSUFFICIENT_FUNDS`.
* If `capture_hold_id` is supplied in settlement request:
  * Look up `account_hold` row, verify `status = 'ACTIVE'`, deduct `held_amount`, and update hold status to `'CAPTURED'`.
* In the **same Oracle local `@Transactional` commit**:
  1. Update `balance_amount` across accounts.
  2. Insert event into `outbox_master`.
* Invalidate Redis `balance_cache:{accountId}` post-commit.

## 4. Strict Rules & Constraints (Do Not Touch)
* **DO NOT touch `transaction_master`.** `accounts-service` owns `account_master`, `account_hold`, and `outbox_master` only.
* Never permit balance or held_amount to go negative (`CHECK >= 0`).
