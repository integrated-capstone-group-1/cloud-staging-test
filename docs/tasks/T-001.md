## 2. In-Scope Contract Slice
* Implement `POST /api/v1/payments` as defined in [`docs/CONTRACTS.md`](file:///c:/Users/RBS83790/OneDrive%20-%20EastWest%20Banking%20Corporation/Documents/training/integrated-capstone/capstone-banking-system/docs/CONTRACTS.md#L155-L215).
* Handle exact currency match (direct transfer) vs shortfall auto-conversion from customer's funding pocket.
* If target pocket has insufficient balance and no funding pocket is supplied, return `422 Unprocessable Entity` with `funding_options` list.
* Validate mandatory header: `X-Idempotency-Key`.
* Invoke `POST /internal/risk/evaluate` synchronously. If latency $> 200\text{ms}$ or score $> 0.85$, reject with `422 DECLINED_HIGH_RISK` or `503 SECURITY_CHECK_UNAVAILABLE`.
* Delegate balance movements to `accounts-service` via `POST /internal/core/settlement`.

---

## 3. Strict Rules & Constraints
* **DO NOT touch `account_master` directly.** `transaction-service` owns `transaction_master` only. Balance mutations MUST go through `CoreBankingClient -> POST /internal/core/settlement`.
* **DO NOT write directly to PostgreSQL `ledger_mutation_audit` in the HTTP path.** Ledger audit records are written asynchronously by the Kafka outbox consumer.
* Use `BigDecimal` with scale 4 for all monetary calculations.

## 4. Done-When Command
```bash
./mvnw test -pl transaction-service -Dtest=PaymentOrchestratorTest
```
Test suite must pass verifying:
1. Exact match payment succeeds with single debit/credit leg call to CBS.
2. Cross-currency shortfall payment constructs 4-leg settlement request (debit customer PHP, credit bank FX, credit fee income, credit recipient EUR).
3. Insufficient balance returns `INSUFFICIENT_FUNDS` with valid quotes and funding options.
4. Risk engine timeout fails closed with `503 SECURITY_CHECK_UNAVAILABLE`.
